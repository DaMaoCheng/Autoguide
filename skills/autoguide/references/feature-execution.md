Inspect actual code and relevant callers, locate the changes, assess related effects, and define acceptance and regression checks. Record and self-review a proportionate plan before editing, then proceed within authorization without routine user approval. Apply this to standalone features as well as integration. For integration, preserve the host architecture and verify affected host workflows; for Bugs, check historical records and current runtime evidence first. Update the affected plan when new evidence changes it.

Build each part according to the confirmed plan and actual dependencies. Before starting each part, read the actual existing implementation and directly reuse what can be reused. After completing the current part, perform actual self-checks against acceptance criteria and testing standards, address related issues, and continue within the authorized scope once checks pass. Do not require user review after each chapter. When important tradeoffs arise during progress, first explain the impacts and options for user operations, results, and maintenance in business language, and help the user understand before deciding. Handle ordinary implementation details within authorization. For new requirements, follow the initiation rules for inclusion in this phase or later phases; do not repeatedly ask about goals or output formats in every round.

## Maintain logs and version records at the feature's location

Keep corresponding records for implementation, maintenance, and actual operation. Archive documentation and logs alongside the feature, and specify their reading entry points. Maintain the following three purposes separately. Do not rewrite raw runtime events as project changes or repair conclusions.

| Record | Purpose | How it is generated |
|-|-|-|
| Changelog | Implementation progress, completed changes, and actual verification results. | AI organizes it by the actual work date during progress or maintenance. |
| Bug log | Actual issues, investigation evidence, causes, solutions, verification results, and actual status. | AI records investigation and repair work by day, retaining the existing identifier for the same issue. |
| Runtime logs | Actual run times, run IDs, key steps, results, exceptions, and retries. | The program or existing logging tool records them automatically, without requiring user or AI intervention for every run. |

Runtime logs automatically create an empty file for each day under the established rules, automatically append events as they occur, and remain empty when no events occur. Startup or recovery must not clear existing files. Use run IDs to connect key steps and actual results. Implement day rollover according to the environment that can actually run, state missing records accurately, and do not fabricate execution results. Before delivery, actually verify automatic recording, day rollover, and appending. Logging does not have to be connected in the very first implementation step.

Read the relevant sections of the Execution and Progress Guide for log fields, detailed recording rules, storage, and verification methods. This track's explicit archive location requirement still applies. For integration, the overall project records may briefly reference the feature record entry points. Keep detailed feature logs alongside the feature and avoid duplicate copying.

Integrated features use the original project's Git repository and version conventions, preserving corresponding changes and feature record entry points without creating a duplicate repository. Standalone features maintain their own Git and version records according to their actual storage location. Uploading to GitHub is not required. Record versions, corresponding code, and actual status at established delivery milestones rather than creating a new version for every log entry or run.

## Verify new features and related existing features against acceptance criteria

Establish initial acceptance criteria and test plans during initiation, and add normal, exceptional, boundary, and connection cases during breakdown, design, and implementation. Use script checks, simulated user operations, or both, selecting according to the actual feature and its impact. Do not merely confirm that code has been written or a command exited successfully.

For integration, check this feature, affected existing features, and related key workflows together. Target behaviors authorized to change should meet this phase's requirements, while existing features outside the scope should remain functioning normally. Base acceptance on the changes and protection scope confirmed during initiation. Do not preserve old behavior that needs changing as a substitute for fulfilling the user's requirements. When reusing shared capabilities, check related consumers. For standalone operation, check its own functionality and actual dependencies, confirming that inputs, results, and usage meet requirements.

Acceptance includes locatable documentation and log entry points, traceable actual execution, and runtime logging functioning normally as agreed. Save actual check results and explicitly identify anything unchecked, failed, or impossible to check because of conditions. Match check depth to impact and risk. Once necessary checks pass, do not repeatedly expand testing without a basis.

When a key mandatory limit or necessary acceptance check fails, continue diagnosing, fixing, and rechecking within existing authorization. Follow the historical Bug and runtime log process for fault handling. If objective conditions or the existing plan cannot meet requirements, explain the actual failure, its impact on the user's work, and feasible options in business language, preserving the actual incomplete status. Pause dependent parts until that condition is met; other authorized work whose prerequisites are met may continue. Do not silently lower mandatory limits or acceptance requirements, or describe unverified effects as promises, to report completion. The user decides important tradeoffs that change confirmed goals or mandatory limits after understanding them.

## Report completion and iterate according to user feedback

After completing the currently authorized work and necessary self-checks, report actual results, verification findings, usage instructions, record locations, version or delivery status, and known limitations. Accurately distinguish implemented, tested, running locally, deployed, and acceptance in the actual environment. Advance later changes, operational adjustments, and iterations according to user feedback. Retain existing implementation, architecture, and UI, and update current documentation and corresponding logs. Do not independently add features, expand scope, or start scheduled tasks.

For claimed business improvements, use the same [Business Impact Criteria](project-initiation.md#distinguish-functional-acceptance-from-business-impact) and existing feature records. Report functional acceptance, actual outcome observations, and effects still awaiting evidence separately. State comparison conditions, observation periods, relevant side effects, and uncertainty. Respect agreed pause or recovery conditions and authorization; a successful feature test does not establish increased sales, and finishing implementation does not authorize starting monitoring or experiments.

When handling a bug, first search historical Bug records for the same or similar issues in this feature and related projects. Then read the corresponding runtime logs by time, feature, error, or run ID. Check this occurrence's actual execution, version, and environment, and reuse applicable solutions. If no applicable historical record exists, continue investigating from actual evidence. Verify repairs in practice, complete the cause, handling, and results in the Bug log, and link the runtime records. Do not alter raw logs or mark unverified items as resolved.

Using Home's configuration mechanism, incorporate stable requirements into applicable project or feature configuration, such as AGENTS.md, CLAUDE.md, or platform settings. These include the current track entry point, stage reading requirements, preserving the architecture when integrating, changing target behaviors as authorized for this phase while protecting existing features outside the scope, verifying affected behaviors and related workflows, archiving documentation and logs alongside the feature, and checking historical solutions alongside runtime logs before fixing bugs. First read and retain valid existing content, explain specific changes and their scope, and check loading and effectiveness. Do not expand a single feature's configuration into global configuration for all projects without authorization.

## How records and configuration support continuity for the current feature

Keep actual entry points for current documentation, changelog, Bug log, and runtime logs at the feature's location. For integration, overall project documentation may reference them. Do not move detailed feature records to unrelated locations or duplicate them. Link code, versions, and records to the same actual change. Record daily progress by day, and maintain versions at agreed delivery milestones.

Automatic runtime logs are implemented by the actual program, script, or existing tools rather than by asking AI to fill them in each day. Create an empty file each day, append when events occur, and locate actual execution by time and run ID. Verify day rollover, event-free days, crossing midnight, appending after restarts, and actual faults according to implementation conditions. Accurately state missing records and unverified conditions. Empty logs cannot prove normal operation.
