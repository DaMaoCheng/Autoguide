## Purpose and reading approach

This guide is for users who understand their business and want to create a project, feature, tool, script, or automation workflow, and for the AI assisting them. The user's business knowledge, experience, and goals are the starting point; AI asks follow-up questions, researches, organizes, broadens the discussion, and implements. The experience behind the guide includes Huang Jincheng's day-to-day collaboration with AI.

1. Read this page first. As needed for the current work, complete platform identification, workspace selection, and configuration additions in [Shared Guide \| Collaboration Preparation and Configuration](shared-preparation.md). Reuse existing information that remains valid; there is no requirement to set up every tool first.
2. Follow the requirements discussion sequence below to establish the current shared understanding and confirm the track, then enter the five stages through the corresponding initiation guide. Before entering the next stage, read the latest applicable guidance; consult the shared methods for specific issues.
3. When goals, the environment, or key conditions change, or when switching conversations or taking over work, check records and handover information using [Shared Guide \| Changes, Records, and Handover](shared-changes.md). Do not reread the entire guide before every small action; if access is restricted, explain what is missing and its impact.

## Collaboration principles throughout the work

- **User direction:** First understand the user's current situation, goals, and viewpoint, then help explore related alternatives. The user decides the direction and important tradeoffs. Do not turn unconfirmed assumptions into requirements or describe unverified methods as proven results.
- **Plain language and patience:** Assume the user is unfamiliar with code. Begin with the purpose, real work, and expected results, without requiring answers to technical questions such as architecture first. Before initiation and throughout the work, use business language to explain how tradeoffs affect daily operations, results, later adjustments, and maintenance, then explain the recommendation's basis. Once the user understands, they decide important tradeoffs; AI handles ordinary implementation details within the authorized scope. Preparation and initiation may take hours or days; proceed according to actual complexity, with no minimum duration.
- **Live online verification:** Verify all AI suggestions and judgments about external facts online before making them. Model memory and existing guide content cannot replace current evidence. Follow [Shared Guide \| Web Research and Evidence Assessment](shared-research.md). Information just verified for the same question may be reused while conditions remain unchanged; verify again when key conditions change.
- **Ongoing consultation:** The rules apply throughout collaboration. Read the latest relevant content as needed when entering a stage, after important changes, and during handover. Shared methods are maintained centrally; track guides retain their specific scope and differing constraints.
- **Choose methods by node:** Prefer explicit code, configuration, or existing tools for clear rules. Evaluate models when understanding, generation, or judgment is actually needed. Match the requirements and deployment environment, prioritizing correctness, stability, speed, explainability, and maintainability, with cost as a secondary consideration.
- **Check premises, data, and effects:** Verify that the problem still holds, that decision inputs are available at the time of use, and that thresholds and weights have a stated basis. Separate functional acceptance from business improvement; use proportionate comparisons and relevant side-effect limits where needed. See [Business Impact](project-initiation.md#distinguish-functional-acceptance-from-business-impact) and [Data and Rule Evidence](project-node-design.md#verify-data-availability-and-rule-evidence). Do not require every small tool to run an experiment.
- **Review and plan before changes:** Before modifying existing code, the AI inspects the actual implementation and callers, determines what and how to change, assesses related effects, and defines acceptance checks. It records and self-reviews a proportionate plan, then proceeds within authorization without routine user confirmation. Read the [Existing-Code Review and Change Plan](shared-changes.md#review-existing-code-and-form-a-change-plan-before-editing).
- **Reuse and records:** Verify reuse and retain applicable frameworks, UI, and shared rules. Maintain update logs and Bug logs by day. Automatically create an empty runtime log file each day and append events automatically, without requiring user or AI intervention each time.
- **Check history before handling Bugs:** First search for the same or similar historical Bugs, then use runtime logs to check the actual process, environment, and version. Verify repairs and add records afterward; do not rewrite original runtime records. Incorporate this requirement into applicable AI configuration.
- **Authorization and reporting:** Continue work, self-checks, and repairs within the authorized scope. Report the outcome truthfully when finished, then make changes according to user feedback. Do not ask again for authorization already given. Before deletion, publication, paid actions, external sending, production operations, or configuration changes outside the existing authorization, explain the target, scope, and consequences and obtain the corresponding authorization.

## Clarify requirements, research and discuss, and confirm the track

First understand how the user works now, the problems they face, why they want a change, the desired results, and the acceptance criteria. In each round, restate the current understanding and ask about key gaps. Before the user has expressed a viewpoint, help them explain their current situation and expectations without proposing a position on their behalf. After they express it, follow [Shared Guide \| Web Research and Evidence Assessment](shared-research.md) to verify and expand on examples, alternative approaches, conditions, advantages, disadvantages, and counterexamples, allowing the user to correct the understanding and make tradeoffs. Users may describe requirements in everyday language without learning to write prompts first. AI organizes the current understanding from information already supplied and asks only about key gaps that affect the current judgment. When the goal and authorization are clear, proceed in that direction without routinely asking what output or format the user wants in each round. When important tradeoffs need discussion, first explain their practical effects, then establish what matters most to the user and what must be avoided. Carry confirmed nonnegotiable requirements through implementation requirements, corresponding checks, and actual results; see the initiation and acceptance guidance in both tracks for details.

```text
Current goal:
Scope and boundaries for this phase:
Key constraints, outcomes to avoid, and acceptance criteria:
Existing foundation and ownership:
Confirmed points, questions for discussion, and assumptions to verify:
```

AI develops this record gradually from the supplied materials; the user need not complete everything at once. The current shared understanding may continue to evolve. Mark unknowns honestly and realign after important changes. Once the user's goal and current scope are understood, use the table below to explain which track currently appears suitable, then let the user confirm it.

| Decision dimension | Project Track | Feature Track |
|-|-|-|
| Goal and current scope | Achieve an overall business result by coordinating several relatively independent capabilities, their connections, the first phase's scope, and later phases. | Create or adjust a feature, tool, script, or automation workflow around one clear capability, with describable inputs, results, and boundaries. |
| Existing foundation and host | May be newly created or integrate or modify existing systems and tools. | May belong to a project, website, or tool, or run independently; may include multiple levels of subfeatures and dependencies on multiple systems. |
| Verification and record priorities | Verify the overall goal, coordination between capabilities, and the complete workflow; manage the overall project plan. | Verify this capability and its dependencies; when attached to an existing host, also check relevant existing features. Archive its documentation and logs with the feature. |

Size, line count, the presence of a UI or server, number of interfaces, independent operation, or the need for refactoring cannot determine the track on their own. Both tracks prioritize reuse; an attached feature does not change the original project's architecture. When the user already has a clear choice, still check it against the actual goal. If the other track fits better, explain why and let the user decide; AI must not change tracks on its own. A project may contain multiple features without creating a separate project for each one.

Example: Exporting selected orders in a specified format can be discussed as a feature even when it involves reading, validation, conversion, and saving. A complete assistant coordinating order management, information matching, file generation, usage records, and quota management is more likely a project. These examples illustrate differences in goals and scope; the user still confirms the actual track.

**The sole entry point after track confirmation:** Save the current requirements and a brief rationale for track selection. For a project, enter [Project Track \| Initiation Guide](project-initiation.md); for a feature, enter [Feature Track \| Initiation Guide](feature-initiation.md). Proceed by stage afterward. If the goal or scope materially changes, realign using the changes guide; ordinary implementation does not require selecting the track again.

## Five-stage index for projects and features

Each track retains its own five documents. Find the entry point for the current stage; detailed rules and completion criteria are in each document. Completion criteria determine which parts can proceed, without introducing approval for every chapter. Where key information is missing, first verify the parts that depend on it; continue authorized work that does not depend on the gap.

**Constraints for feature scenarios:** First establish whether the feature is attached or independent, and its actual ownership. When attached, build within the existing architecture; shared standards must not become a reason to refactor the project. Modify target behavior as explicitly authorized for this phase, and keep existing features outside that scope working normally. Acceptance checks cover the target change and related workflows. Archive documentation and all three log types with the feature, and follow the original project's Git conventions. Build independent features for their actual environment.

## Maintaining and extending this guide

This section is for maintainers. Develop methods from real work, experience, and conversations, distinguishing requirements, implementation, and actual results. State the conditions for examples; do not turn a single unverified experience directly into a general rule. When changing detailed rules, also check the corresponding guides, index, keywords, and configuration examples. Link to the same current standard to avoid maintaining duplicate bodies of text. Record the version and date when maintaining or installing copies. Project materials, accounts, and runtime logs do not become public by default through use of this publicly available guide.

Home retains the purpose, core principles, and navigation entry points. Platform configuration, research, changes, and recording methods are maintained in the shared guides; stage details are maintained in the corresponding tracks. Specific tool recommendations still require live verification. Reference for scope and reuse: [GOV.UK: Solve a Whole Problem for Users](https://www.gov.uk/service-manual/service-standard/point-2-solve-a-whole-problem). Track classification and this guide's constraints come from the collaboration agreement; do not impose external classifications or a particular platform.
